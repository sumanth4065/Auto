# Generate README Command

Scans the repository to produce or refresh a `README.md` at the repo root. Covers:

- A plain-language description of what the repository does and who it is for
- A catalog of every Lambda function, API Gateway, and plugin/shared library
- A catalog of DynamoDB tables with key schema and access patterns
- A catalog of other AWS service usage (S3, SQS, SNS, EventBridge, Secrets Manager, etc.)
- A catalog of external service integrations: Guidewire (PolicyCenter, BillingCenter, ClaimCenter) and Huon service endpoints
- Links to architecture diagrams generated by `/generate-architecture`

When an existing `README.md` is found, its content is used to **enhance and improve** the new iteration — extracting richer descriptions, preserving custom sections, and carrying forward any prose the developer has written. When no `README.md` exists, the user is prompted for seed information before generation begins.

Pass `--update` to refresh an existing README rather than replace it wholesale — existing prose sections are preserved and only the generated catalog and diagram sections are updated.

## Arguments

- `--update` (optional): Merge into the existing `README.md` instead of replacing it. Catalog and diagram sections are regenerated; handwritten prose sections are left untouched.

## Workflow

### Step 0: Seed from Existing README or Prompt User

**If `README.md` exists at the repo root:**

Read the entire file before doing anything else. Extract and record the following for use in later steps:

- **Description / intro block**: The text immediately after the `# Title` heading (up to the first `##` heading or `---`). This is the best source of project description — prefer it over `package.json`.
- **Custom sections**: Any `##` sections whose headings do not match the standard generated sections (API Gateways, Lambda Functions, Plugins & Shared Libraries, DynamoDB Tables, AWS Services, External Integrations, Architecture, API Reference, Documentation, Getting Started, Development, Table of Contents). These are developer-written sections that must be preserved exactly and included in the new TOC.
- **Getting Started / Development prose**: Capture these verbatim — they contain handwritten instructions that must never be replaced.
- **Any badges, shields, or logo blocks** at the top of the file — preserve them verbatim above the title or description.
- **Enhancement signal**: Note which sections are thin or auto-generated (tables only, no prose) vs. sections that have been hand-enriched. Use the hand-enriched content as the gold standard for that section's description in the new README.

Use the existing README to produce a *better* version — richer descriptions pulled from the prose, improved catalog context, and all custom sections carried forward. The new README should be a superset of the old one, never a downgrade.

**If no `README.md` exists:**

Before reading any code, prompt the user for seed information that cannot be inferred from the repo. Ask all questions in a single interactive prompt:

```
No README.md found. Let's gather some context before generating one.

1. What does this project do? (1–3 sentences)
   > 

2. Who are the primary users? (e.g., internal developers, end-users via a web app, other services)
   > 

3. Are there any key features, integrations, or constraints worth highlighting?
   > 

4. Does this project integrate with Guidewire (PolicyCenter, BillingCenter, ClaimCenter) or Huon services? If so, which ones?
   > 

5. Who owns or maintains this project? (team name, Slack channel, or email — optional)
   > 

6. Any special local setup steps beyond "npm install"? (optional)
   > 
```

Store the answers. Use them to populate the description block, Getting Started, and Development sections. If the user skips a question, derive the answer from the repo instead.

### Step 1: Read the Repository Shape

Collect everything needed before writing a single line of output.

**Identity**
- Read `package.json` (root and any workspace roots) for `name`, `description`, `version`, and `workspaces`.
- Read `lerna.json`, `nx.json`, or `turbo.json` if present — note the monorepo tool and package glob patterns.
- Read the first non-empty paragraph of any existing `README.md` as the current description baseline (already captured in Step 0).

**Infrastructure config** — use the same discovery priority as `/generate-openapi-spec`:
1. `serverless.yml` / `serverless.yaml` — `functions`, `events.http`, `provider`, `environment`
2. CDK stacks (`*stack*.ts`, `*api*.ts`) — `RestApi`, `HttpApi`, `addResource`, `addMethod`
3. SAM / CloudFormation (`template.yaml`, `template.json`) — `AWS::ApiGateway::*`, `AWS::Serverless::*`, `AWS::Lambda::Function`
4. Any existing `openapi*.yaml` / `swagger*.json` — extract the `paths` block for route inventory

**Lambda inventory** — for each Lambda identified in the infrastructure config:
- Handler file path
- Function name and logical purpose (derive from the handler name, file path, and the first JSDoc comment or `// ` comment at the top of the file if present)
- HTTP method + path it is bound to (or "event-driven" if not HTTP)
- Runtime and timeout (from config)
- Any IAM roles or environment variables declared

**Plugin / shared library inventory** — scan for:
- `packages/` or `libs/` directories
- Any directory with its own `package.json` whose `name` starts with `@` (scoped packages)
- Files under `.claude/` (commands, hooks, agents, scripts) if this is a Claude Code plugin repo

**Existing `docs/` directory** — recursively list all files in `docs/` and categorize them:

| Category | Match pattern | Use |
|---|---|---|
| Architecture diagrams | `*.drawio`, `*.mermaid`, `architecture*.md` | Linked in Architecture section |
| OpenAPI / Swagger specs | `openapi*.yaml`, `openapi*.json`, `swagger*.yaml`, `swagger*.json` | Linked in API Reference section |
| Markdown documents | all other `*.md` files | Linked in Documentation section |
| Other assets | everything else (images, PDFs, etc.) | Listed in Documentation section |

For each `.md` file found (excluding `architecture*.md`), derive a human-readable title from the filename (kebab/snake to title case, strip extension). If the file starts with a `# Heading`, use that heading as the title instead.

**OpenAPI spec** — apply the category table above; also accept a custom path if one was passed to `/generate-openapi-spec`. If found, record the path — it will be linked in the README's API Reference section. If not found, note it as absent but do not block the rest of the command.

**DynamoDB inventory** — scan for table definitions across all infrastructure config sources:
- Table names declared in `serverless.yml` under `resources.Resources` (`AWS::DynamoDB::Table`)
- CDK `Table` constructs in stack files
- SAM / CloudFormation `AWS::DynamoDB::Table` resources
- Also scan Lambda handler source files and any `@lib/` shared code for `TableName` references, `DynamoDB.DocumentClient` calls, and `process.env.*TABLE*` / `process.env.*DYNAMO*` env vars — these surface tables not declared in IaC

For each table, record:
- Table name (or env var name if the physical name is dynamic)
- Partition key and sort key (names + types)
- GSIs / LSIs if declared
- Which Lambda functions access it (read / write / both)
- TTL attribute if set

**AWS services inventory** — beyond Lambda, API Gateway, and DynamoDB, scan IaC and handler source for usage of:

| Service | Signals to look for |
|---------|-------------------|
| S3 | `AWS::S3::Bucket`, `s3.putObject`, `s3.getObject`, bucket env vars |
| SQS | `AWS::SQS::Queue`, `sqs.sendMessage`, queue URL env vars |
| SNS | `AWS::SNS::Topic`, `sns.publish`, topic ARN env vars |
| EventBridge | `AWS::Events::Rule`, `eventbridge.putEvents`, event bus env vars |
| Secrets Manager | `secretsmanager.getSecretValue`, secret ARN env vars |
| SSM Parameter Store | `ssm.getParameter`, parameter path env vars |
| Step Functions | `AWS::StepFunctions::StateMachine`, `stepfunctions.startExecution` |
| Cognito | `AWS::Cognito::UserPool`, Cognito client env vars |
| CloudFront | `AWS::CloudFront::Distribution` |

Record each service found: the resource name/ARN (or env var), which Lambdas use it, and its purpose (derive from variable name or context).

**External integrations inventory** — scan handler source files, config files, and env vars for outbound HTTP calls to external systems:

*Guidewire* — look for:
- `GUIDEWIRE_*`, `GW_*`, `POLICY_CENTER_*`, `BILLING_CENTER_*`, `CLAIM_CENTER_*` env vars
- Imports or references to Guidewire client libraries or shared wrappers (e.g. `@lib/guidewire`, `guidewire-client`)
- Hostnames containing `guidewire`, `policycenter`, `billingcenter`, `claimcenter`
- REST or SOAP calls to Guidewire APIs

For each Guidewire integration found, record: system (PolicyCenter / BillingCenter / ClaimCenter), endpoint or path pattern, HTTP method, and purpose.

*Huon* — look for:
- `HUON_*` env vars
- Imports referencing `huon` client libraries or shared wrappers (e.g. `@lib/huon`, `huon-client`)
- Hostnames containing `huon`
- Any service-to-service calls that resolve to Huon endpoints

For each Huon integration found, record: service name, endpoint or path pattern, HTTP method, and purpose.

*Other external services* — also note any other third-party API calls (payment processors, address validators, etc.) discovered via env vars or fetch/axios base URLs not matching the app's own API Gateway domain.

### Step 2: Draft the Repository Description

Write a 2–4 sentence description that answers:
1. What does this repository do?
2. Who uses it (developers, end-users, other services)?
3. What is the primary AWS/cloud pattern (API Gateway + Lambda, event-driven, etc.)?

Source material in priority order:
1. Existing README intro (captured in Step 0) — use as-is if already rich; improve it if thin
2. User-provided seed answers (Step 0 prompt, if no README existed)
3. `package.json` description
4. Folder/function names as last resort

If `--update` is passed and a handwritten intro already exists and is not thin (more than one sentence), keep it verbatim — do not rewrite it.

---

### Step 3: Build the Catalog

Produce three catalog sections in markdown.

#### 3a — API Gateways

For each API Gateway found:

```markdown
## API Gateways

| Gateway | Base Path | Stage | Auth | Description |
|---------|-----------|-------|------|-------------|
| MyApi   | /my-api   | prod  | JWT  | Handles X   |
```

#### 3b — Lambda Functions

Group Lambdas by their API Gateway (or "Event-Driven" for non-HTTP triggers). For each Lambda:

```markdown
## Lambda Functions

### MyApi

| Function | Method | Path | Handler File | Timeout | Purpose |
|----------|--------|------|--------------|---------|---------|
| cfc-flow-director | POST | /flow-director-v2 | src/flow-director/handler.ts | 30s | Orchestrates workflow |
```

Include a "Purpose" column — derive it from the first comment/JSDoc in the handler, or from the function name if no comment exists.

#### 3c — Plugins & Shared Libraries

```markdown
## Plugins & Shared Libraries

| Name | Path | Type | Description |
|------|------|------|-------------|
| @lib/lambda-shared | libs/lambda-shared | Internal lib | Middleware, logging, response helpers |
| claude-plugin | . | Claude Code plugin | Distributes commands, hooks, and agents |
```

Type is one of: `Internal lib`, `Claude Code plugin`, `NPM package`, `CDK construct`.

#### 3d — DynamoDB Tables

For each table discovered:

```markdown
## DynamoDB Tables

| Table | Partition Key | Sort Key | GSIs | Used By | Purpose |
|-------|--------------|----------|------|---------|---------|
| cfc-policies | policyId (S) | — | statusIndex (status, createdAt) | cfc-flow-director, cfc-initial-data | Stores policy state during CFC workflow |
| cfc-sessions | sessionId (S) | — | — | cfc-flow-director | Tracks user session and step progress |
```

If the physical table name is resolved from an env var, show it as `${TABLE_ENV_VAR}`. Omit the GSIs column if no table has any. If no DynamoDB tables are found, write a single note: `No DynamoDB tables declared in infrastructure config.`

#### 3e — AWS Services

For each non-Lambda/Gateway/DynamoDB AWS service found, group by service type:

```markdown
## AWS Services

### S3
| Bucket | Env Var | Used By | Purpose |
|--------|---------|---------|---------|
| ${DOCUMENTS_BUCKET} | DOCUMENTS_BUCKET | cfc-complete-auto-ao | Stores signed document PDFs |

### SQS
| Queue | Env Var | Used By | Purpose |
|-------|---------|---------|---------|
| ${NOTIFY_QUEUE_URL} | NOTIFY_QUEUE_URL | cfc-record-notes | Publishes note events for downstream processing |

### Secrets Manager
| Secret | Env Var | Used By | Purpose |
|--------|---------|---------|---------|
| ${GW_SECRET_ARN} | GW_SECRET_ARN | cfc-flow-director | Guidewire API credentials |
```

Only include service headings (`### S3`, `### SQS`, etc.) for services that are actually present. If no additional AWS services are found beyond Lambda, API Gateway, and DynamoDB, omit this section entirely.

#### 3f — External Integrations

Produce a sub-sectioned table for each external system found:

```markdown
## External Integrations

### Guidewire PolicyCenter
| Endpoint | Method | Used By | Purpose |
|----------|--------|---------|---------|
| /bc/rest/account/v1/accounts/{id} | GET | cfc-initial-data | Fetch account billing details |
| /pc/rest/policy/v1/policies/{id}/vehicles | GET | cfc-initial-data | Retrieve vehicles on policy |

### Guidewire BillingCenter
| Endpoint | Method | Used By | Purpose |
|----------|--------|---------|---------|
| /bc/rest/lienholder/v1/lienholders | POST | cfc-complete-auto-ao | Create or update lienholder record |

### Huon Services
| Service / Endpoint | Method | Used By | Purpose |
|--------------------|--------|---------|---------|
| /huon/address/v2/verify | POST | cfc-verify-address | Validate and standardize finance company address |
```

Use a separate `###` sub-section for each distinct external system (PolicyCenter, BillingCenter, ClaimCenter, Huon, and any others). If an endpoint URL is dynamic (env-var-driven host), show it as `${GW_BASE_URL}/path`. If no external integrations are found, omit this section entirely.

### Step 4: Build the Table of Contents

The Table of Contents must be **dynamically generated** from the actual sections present in the final README — not hardcoded. Follow these rules:

1. **Collect all `##` headings** from the assembled document in order. Include both standard generated sections and any custom sections carried forward from the existing README.

2. **Generate a GitHub-compatible anchor** for each heading:
   - Lowercase the heading text
   - Replace spaces with hyphens `-`
   - Remove all characters that are not alphanumeric, hyphens, or spaces (before hyphenation)
   - Examples:
     - `## API Gateways` → `#api-gateways`
     - `## Plugins & Shared Libraries` → `#plugins--shared-libraries`
     - `## Getting Started` → `#getting-started`
     - `## My Custom Section` → `#my-custom-section`

3. **Render the TOC** as a flat list of anchor links:

```markdown
## Table of Contents

- [API Gateways](#api-gateways)
- [Lambda Functions](#lambda-functions)
- [Plugins & Shared Libraries](#plugins--shared-libraries)
- [DynamoDB Tables](#dynamodb-tables)
- [AWS Services](#aws-services)
- [External Integrations](#external-integrations)
- [Architecture](#architecture)
- [API Reference](#api-reference)
- [Documentation](#documentation)
- [Getting Started](#getting-started)
- [Development](#development)
- [My Custom Section](#my-custom-section)
```

Sections that are omitted from the README (e.g. no AWS services found) must also be omitted from the TOC — only link sections that are actually present in the document.

4. **Include every `##` section** in the TOC — do not hardcode a fixed list. If the final README has a custom section like `## Runbook` or `## Team`, it must appear in the TOC.

5. **Do not include `###` sub-headings** in the main TOC (e.g., Lambda sub-groups by gateway). Keep the TOC at the `##` level only.

**`--update` merge rules:**
- If a section heading already exists in the current README, replace only its content — do not move its position.
- If a section is new (not in the current README), append it before the last `---` separator or at the end of the file.
- Never delete a section that exists in the current README, even if the catalog no longer contains entries for it.
- Preserve all prose the developer has written manually.
- Always regenerate the TOC at the end of the merge to reflect the actual final set of sections.

## Usage Examples

```bash
# Create README.md from scratch (prompts for seed info if no README exists)
/generate-readme

# Refresh catalog and diagrams in an existing README, preserving handwritten prose
/generate-readme --update
```

---

## Notes

- This command only writes `README.md`. It reads but never overwrites any file in `docs/` — those files are owned by `/generate-openapi-spec`, `/generate-architecture`, or the developer.
- The Table of Contents is always fully regenerated from the actual sections in the final file — it is never hardcoded.
- If the repo has no discoverable infrastructure config (no `serverless.yml`, CDK, SAM, or `openapi*.yaml`), the catalog sections are written with a placeholder row and a note that no config was found.
- When an existing README is found, the new version should always be at least as good — richer descriptions, no lost prose, all custom sections preserved.
- Run `/generate-architecture` first to create diagram files, then `/generate-readme` (or `/generate-readme --update`) to link them.
- Run `/generate-openapi-spec` first if you want the README API Reference section to link a freshly regenerated spec.
